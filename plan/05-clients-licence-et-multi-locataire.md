# 05 : CRM Pro chez des clients, licence de KumoMTA, multi-locataire, campagnes (30/10/2026)

Version condensée du rapport du concepteur (lecture seule, sources web consultées le 30/10/2026, constats d'agent non rejoués). Certitudes : élevée / moyenne / faible.

## A. Risque que KumoMTA devienne payant
- Licence Apache-2.0 (dépôt KumoCorp/kumomta). L'éditeur Kumo Corp vend du SUPPORT (Silver dès 5 000 $/an, Gold dès 10 000 $/an), aucun module fermé trouvé. Aucun engagement écrit de rester libre. Pas de CLA mentionné. Versions régulières (dernière vue : 2026.09.29). Ubuntu 24.04 absente de la liste des paquets de la doc lue : à vérifier.
- Précédents de relicenciement : HashiCorp (MPL vers BSL, 2023), Elastic (Apache vers SSPL/ELv2, 2021), Redis (BSD vers RSAL/SSPL, 2024, puis AGPL avec Redis 8 en 2025). Probabilité pour KumoMTA à 3-5 ans : faible à moyenne, non mesurable. Une communauté de la taille de KumoMTA (environ 568 étoiles) ne ferait pas forcément un « Valkey ».
- GARANTI : chaque version déjà publiée sous Apache-2.0 le reste pour toujours (licence irrévocable). Un changement ne vise que les versions suivantes. On ne peut pas garantir qu'il ne deviendra jamais payant ; on peut garantir que cela ne coûterait aucune licence et ne bloquerait aucun envoi.
- Protections : (1) figer une version avec empreinte SHA-256 ; (2) copie du code et des binaires (copie publique, image GHCR publique, archive sur Backblaze B2) ; (3) contrat d'interface `ServeurEnvoi` agnostique, déjà dans le cahier (REQ-INF-029), aucun écran ni table au nom de KumoMTA ; (4) deuxième réalisation Postfix + rspamd (ou OpenDKIM) testée, avec les mêmes tests ; (5) coût de bascule estimé 8 à 15 jours-agent, SANS nouvelle chauffe (la réputation suit les IP et domaines) ; (6) garde de CI sur l'empreinte et cargo-deny.
- Autres briques : Postgres (licence PostgreSQL), PostGIS (GPL-2.0+, lien vers les sources dans NOTICE si on publie l'image), Laravel/React/Vite (MIT), Caddy/Playwright (Apache-2.0), nginx (BSD-2). ATTENTION Redis : rester en 7.2 (BSD) ou passer à Valkey ; ne pas monter à 7.4 ou plus sans décision.
- Déployer KumoMTA chez des clients : AUCUN problème de licence (certitude élevée). Obligations : texte de la licence, fichier NOTICE, signaler les fichiers modifiés ; ne pas utiliser la marque « KumoMTA » comme nom de produit.

## B. Déploiement chez des clients
- Le multi-locataire existe dans le schéma (l'espace de travail est le locataire, RLS Postgres sur environ 55 tables) mais son efficacité en production n'est PAS prouvée : CRM_DB_APP_ROLE_ENABLED=false par défaut, le dépôt se contredit (CoverageRefreshMatrix.php:25 contre PartmanMaintenir.php:110), la suite de tests ne peut pas tourner sous le rôle de production (RlsTest.php:323-347).
- Le code contient des règles propres à Axion (espaces figés `axion-ia` et `vivier-candidats`, synchro console, gardes « Axion » du cahier : plan lignes 1626, 2638, 4957, REQ-SEC-004).
- Trois modèles comparés. RECOMMANDÉ : hybride. D'abord UNE INSTALLATION PAR CLIENT (jamais dans la base d'Axion), qui sert aussi la vente directe sur le serveur du client. Une instance mutualisée « petits clients » plus tard, seulement si : RLS mesurée active en prod, tests sous rôle applicatif, test à deux clients factices vert, audit Opus sécurité.
- À créer : édition « produit » sans les traitements propres à Axion ; RLS armée par défaut ; création de client (commande et écran) ; configuration par client hors git ; marque du client ; mesure d'usage et quotas remontés à la console des automatisations ; diagnostic par client ; export complet des données.
- Juridique : le client est l'expéditeur et le responsable de traitement, Axion son sous-traitant (art. 28 : contrat, registre, sous-traitants ultérieurs, art. 32). Information art. 14 au nom du client, bloquante avant toute campagne. Le client garantit la base légale de ses fichiers (case obligatoire à l'import). La base de prospection d'Axion n'est jamais fournie aux clients. Liste d'opposition par client (liste technique commune possible pour pièges et adresses invalides). Aucun pixel de suivi.
- CONFLIT À TRANCHER : « jamais de suppression à la fin d'un client » (Will, 26/10) contre l'art. 28.3.g (le sous-traitant supprime OU renvoie, au choix du client). Proposition : rendre les données au client par export ; n'archiver que sur ordre écrit du client.
- Envoi : domaines au nom de chaque client, jamais partagés ; au moins une IP dédiée par client pour le froid ; chauffe par client (6 à 9 semaines) ; serveur d'envoi de préférence sur le compte d'hébergement du client (une plainte ou un blocage du port 25 ne touche que lui) ; PIÈGE : le « tenant » KumoMTA doit être imposé par l'identité de connexion SMTP, jamais lu dans un en-tête X-Tenant ; le mot « tenant » est déjà utilisé pour une file par boîte dans le plan (ligne 1228) : figer une convention dans l'ADR. Port 25 : une demande par compte d'hébergement.
- Coût direct estimé (faible certitude) : environ 25 à 60 € HT par mois et par client, sans licence, plus 1 à 2 jours de mise en place et 6 à 9 semaines de chauffe.
- Exploitation : une seule image publique (GHCR, CI gratuite), chaque instance TIRE sa version (aucune clé SSH de client dans GitHub) ; ordre Axion, pilote, tous ; coupure d'urgence ; migrations compatibles avec la version précédente ; sauvegarde chiffrée par client sur B2, restauration testée chaque mois ; secrets par client hors git ; registre des clients hors dépôt public ; support par page de diagnostic.
- Dépôt public pour un produit vendu : aucun secret, aucun nom de client, aucune IP dans le code ; gitleaks et garde données personnelles obligatoires. Licence actuelle « propriétaire », sans fichier LICENSE : recommandé de garder « propriétaire, source visible » avec un LICENSE ; AGPL possible plus tard. Aucune branche ni code par client.
- Lien avec la console des automatisations : le CRM chez un client est une automatisation vendue avec forfait et volumes remis à zéro à la date anniversaire ; l'usage remonte par API signée ; un dépassement informe, ne bloque pas (ordre de Will).

## C. Campagnes
- Le cahier (83 exigences CAM, plus CHA, RET, CON, VER, RES) couvre les campagnes de prospection complètes : ciblage, éligibilité, pression commerciale, gabarits, A/B, séquences de 1 à 4 étapes, planification, validation, réponses, rebonds, plaintes, désinscription RFC 8058, statistiques sans pixel, presse.
- Manque pour « complet » : lettre d'information et campagnes à des abonnés consentants (REQ-CAM-065 la sort du module ; sans MailWizz elle ne peut passer que par le moteur du CRM, ce qui tranche D-90) avec formulaires à double confirmation, centre de préférences, éditeur de gabarits, version web, groupe d'IP séparé ; campagnes déclenchées par un événement.
- Ajouts dus au multi-client : identité, domaines, IP, chauffe, seuils, arrêt d'urgence et liste d'opposition PAR CLIENT (plus un arrêt général Axion) ; gardes « Axion » rendues « par client » ; textes légaux par client ; retours routés vers le bon espace avec test à deux clients ; assistant de mise en place DNS et demande de port 25 ; politique d'usage acceptable au contrat.

## E. Pièges
Fuite entre clients si la RLS n'est pas armée ; tenant falsifié ; plainte pour abus qui ferme le compte d'hébergement d'Axion ; secret de client dans le dépôt public (perdu) ; Redis monté en 7.4+ ; KumoMTA mis à jour sans vérifier la licence ; migrations incompatibles entre instances ; conflit suppression / art. 28.3.g ; coûts fixes par client.
